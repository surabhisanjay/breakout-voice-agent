# Deterministic Conversation Improvement Plan

Date: 2026-06-24

Scope: current production/demo path only: Vapi -> FastAPI -> backend deterministic response generation.

This plan does not assume OpenAI prompt-composer availability. Prompt updates can still improve future LLM rewriting, but they do not fix the current production path unless the backend first routes, retrieves, recommends, and composes the right deterministic answer.

## Production Path

Current response generation is mostly deterministic:

1. Vapi sends the customer turn to FastAPI.
2. `dispatch()` routes through `src/orchestration/conversation_manager.py`.
3. `ConversationManager.determine_routing()` selects `InboundAgent` or `BookingAgent`.
4. `InboundAgent.handle_message()` extracts memory, classifies intent, calls `RecommendationEngine`, and builds a deterministic response through `_fallback_response()`, `_get_faq_or_knowledge_answer()`, `_recommendation_response()`, `_guided_response()`, and `_answer_faq()`.
5. `BookingAgent.handle_message()` owns active booking state, slot handling, booking FAQs, availability, cart creation, and booking creation.
6. `ResponseComposer` exists, but the production requirement must not depend on an OpenAI-backed rewrite.

## Classification Key

- A. Prompt-only
- B. Deterministic backend fix
- C. Recommendation-engine fix
- D. Knowledge retrieval fix
- E. Routing/state-management fix

Most production issues below are B/C/D/E. Very few are A because the current Vapi + FastAPI path speaks through deterministic code.

## Evidence From Current Baseline

The current quality baseline showed no improvement after prompt/playbook changes in the key weak scenarios:

- S08 scary/horror preference: unchanged.
- S10 budget-sensitive customer: unchanged.
- S11 price objection: unchanged.
- S17 slot comparison: unchanged.
- S19 location comparison: unchanged.
- S24 customer confusion: unchanged.
- S25 customer frustration: unchanged.

That is expected because these failures are generated by routing, deterministic answer selection, recommendation logic, and knowledge lookup rather than OpenAI composition.

## Issue 1: Weak Comparison Answers

Classification: B, C, D, E

Observed behavior:

- Slot comparisons and room comparisons can produce a room monologue or generic description instead of answering the comparison.
- Example from S17: asking whether to choose an earlier/later slot or asking about being late can return a Murder Mystery description.

Root cause:

- `src/services/question_classifier.py::QuestionClassifier.classify()` detects broad recommendation/FAQ intent, but does not preserve a specific `slot_comparison`, `room_comparison`, or `timing_tradeoff` subtype.
- `src/orchestration/conversation_manager.py::determine_routing()` routes broad recommendation questions to `InboundAgent`, where the exact comparison intent can be lost.
- `src/agents/inbound_agent.py::_get_faq_or_knowledge_answer()` calls demo knowledge, FAQ, contextual recommendation, and room-name explanations. If the query includes a room name, `_answer_room_name()` can win even when the user is comparing options.
- `src/agents/inbound_agent.py::_comparison_response()` only handles a few room-pair cases and is not a general comparator.

Fix plan:

1. Extend `QuestionClassifier` with deterministic subtopics:
   - `slot_comparison`
   - `room_comparison`
   - `location_comparison`
   - `timing_tradeoff`
2. In `InboundAgent._get_faq_or_knowledge_answer()`, check comparison subtopics before room descriptions.
3. Add deterministic comparison helpers:
   - `compare_rooms(room_a, room_b, memory)`
   - `compare_slots(slot_a, slot_b, memory)`
   - `compare_locations(location_a, location_b, memory)`
4. For slot/timing comparison, answer the customer’s question first:
   - If they mention lateness, recommend the later slot.
   - If they ask “which is better”, ask whether they prefer earlier arrival or more buffer only if no preference is given.
5. Keep booking state active after the answer.

Validation scenarios:

- “Should I take 3:15 or 5:30?”
- “I may be late, which slot is safer?”
- “Compare Murder Mystery and Hostage.”
- “Which is better for beginners, Murder Mystery or Hostage?”

Expected style:

“If you might be late, take 5:30. It gives you more buffer, and the game needs briefing time before it starts. Want me to hold that slot?”

## Issue 2: Weak Location Recommendations

Classification: B, C, D

Observed behavior:

- Location questions often list all branches instead of guiding the customer.
- Example from S19: “Which location is better from Marathahalli?” returns only “Breakout has locations in Koramangala, Whitefield, and JP Nagar.”

Root cause:

- `src/agents/inbound_agent.py::_answer_faq()` handles location questions with a static branch list.
- `src/knowledge/demo_knowledge.py::get_demo_answer()` also returns generic location answers.
- No deterministic location guidance table maps common Bangalore neighborhoods or customer needs to likely branches.
- `RecommendationEngine` recommends rooms, not locations.

Fix plan:

1. Add a small, auditable location guidance layer, either in `RecommendationEngine` or a new deterministic helper:
   - `recommend_location(origin_or_preference, memory)`
2. Seed it with conservative mappings only where confidence is high:
   - Marathahalli / Brookefield / Hoodi / ITPL -> Whitefield
   - HSR / Indiranagar / MG Road / central Bangalore -> Koramangala, with caveat if uncertain
   - South Bangalore / Jayanagar / Banashankari -> JP Nagar
3. When no mapping exists, give a practical answer rather than a flat list:
   - “Tell me where you’re coming from and I’ll narrow it down.”
4. Keep inventory-aware wording:
   - If a room is already selected, only recommend locations where that room exists.

Validation scenarios:

- “Which location is closer from Marathahalli?”
- “I’m near Indiranagar. Which branch should I choose?”
- “Which location has Undercover?”
- “Which branch is best for kids?”

Expected style:

“From Marathahalli, Whitefield is usually the first branch I’d check. It also has Murder Mystery, Hostage, Undercover, and Bomb Defusal. Want to use Whitefield?”

## Issue 3: Poor Confusion Handling

Classification: B, D, E

Observed behavior:

- Direct education questions can be followed by qualification instead of a clear explanation.
- Example from S24: “I’m confused. What exactly happens inside an escape room?” can lead to “How many people are joining?” too early.

Root cause:

- `src/services/question_classifier.py::_is_faq_question()` detects “what happens”, but the generated answer can still fall through into qualification if the exact knowledge handler misses the phrase.
- `src/agents/inbound_agent.py::_is_escape_room_education_query()` misses variants like “what exactly happens inside an escape room”.
- `src/agents/inbound_agent.py::_escape_room_education_response()` exists but is not consistently prioritized before qualification.
- `ConversationIntelligenceLayer.get_consultative_selling_reply()` has first-timer guidance but not a deterministic confusion-repair answer.

Fix plan:

1. Expand escape-room education detection to cover:
   - “what exactly happens”
   - “what happens inside”
   - “I’m confused”
   - “how does this work”
   - “what do we actually do”
2. Run education/confusion handling before qualification prompts.
3. Add a short deterministic confusion response:
   - What happens
   - Staff briefing and monitoring
   - One gentle next step
4. Resume the current booking or qualification field after answering, only if the answer does not already end with a question.

Validation scenarios:

- “I’m confused. What exactly happens inside an escape room?”
- “What do we actually do inside?”
- “I’ve never done this before. How does it work?”

Expected style:

“Totally fair. You enter a themed mission, search for clues, solve puzzles as a team, and the staff brief you before the game. If you want, I can suggest an easy first room.”

## Issue 4: Poor Frustration Repair

Classification: B, E

Observed behavior:

- Frustrated repair turns can fall into generic fallback or contact collection.
- Example from S25: “No, that’s not what I asked” can lead to “May I take your name and number…” instead of repairing the conversation.

Root cause:

- `src/services/question_classifier.py` supports `repair`, but `ConversationManager.determine_routing()` keeps repair on the current agent and `InboundAgent._fallback_response()` usually repeats the previous question.
- `src/agents/sentiment_agent.py` detects frustration and repair phrases, but sentiment output is not consumed early enough by deterministic response composition.
- `src/agents/conversation_intelligence_agent.py` records “Response quality concern” after the fact; it does not influence the immediate recovery response.

Fix plan:

1. Add an immediate deterministic repair handler before generic fallback/contact collection:
   - Detect “no no no”, “that’s not what I asked”, “you’re not understanding”, “stop asking”.
2. Response should:
   - Acknowledge
   - Avoid defensiveness
   - Restate the customer’s likely goal if known
   - Ask one corrective question only if needed
3. If booking state exists, resume booking after repair.
4. If sentiment risk is high or the customer requests human help, EscalationAgent still wins.

Validation scenarios:

- “No no no, that’s not what I asked.”
- “You are not understanding.”
- “Stop asking me the same thing.”

Expected style:

“You’re right. I missed the actual question. You’re asking about the difference between those two rooms. Murder Mystery is calmer and investigation-led; Hostage is more urgent. Which mood do you want?”

## Issue 5: Ignored Horror / Thrill Preferences

Classification: B, C, E

Observed behavior:

- Horror or thrill preferences can be ignored while the agent asks for participant count.
- Example from S08: “Do you have something scary?” can produce “How many people are joining?”

Root cause:

- `src/services/recommendation_engine.py::recommend()` handles beginner, challenging, story, adults, kids, and events, but does not explicitly handle horror/scary/thrill language.
- `ConversationMemory` may store `challenge_preference`, but the recommendation branch mainly checks `challenging`, `story`, and `beginner`.
- `src/agents/inbound_agent.py::_guided_response()` prioritizes missing qualification fields before answering the preference in some paths.

Fix plan:

1. Add preference extraction for:
   - `scary`
   - `horror`
   - `thrill`
   - `intense`
   - `not too easy`
   - `intermediate`
2. Add deterministic no-horror policy if there is no verified horror offering:
   - Do not invent horror/jump-scare rooms.
   - Offer closest verified suspense/pressure options.
3. `RecommendationEngine.recommend()` should use location and inventory:
   - Whitefield: Bomb Defusal for pressure, Undercover for story tension.
   - Koramangala: Classified or Undercover for challenge/story tension.
   - JP Nagar: Missile Attack/Prison Break if present in verified inventory, otherwise Murder Mystery/Hostage based on inventory.
4. Answer the preference first, then ask one missing field.

Validation scenarios:

- “Do you have something scary?”
- “We want thrill, not too easy.”
- “Which room is most intense at Whitefield?”
- “We want horror.”

Expected style:

“We don’t position the rooms as horror or jump-scare games. If you want suspense and pressure, I’d look at Bomb Defusal at Whitefield or Classified at Koramangala. Which location works for you?”

## Issue 6: Weak Budget Conversations

Classification: B, D, E

Observed behavior:

- Budget-sensitive birthday/package questions can route into qualification.
- Price objections can lead to contact collection before answering the price/discount uncertainty.

Root cause:

- `src/agents/inbound_agent.py::_guided_response()` asks birthday/corporate qualification fields before providing budget framing.
- `src/agents/inbound_agent.py::_answer_faq()` has a generic budget response and can offer “quote or estimate,” but this is not grounded in a clear product path.
- `knowledge/faq.txt` contains explicit discount claims. These must be treated as business-source data only if confirmed safe for production; otherwise deterministic responses should avoid quoting them.
- `src/agents/booking_agent.py` has safer active-booking discount wording, but inbound/general flows still need consistent behavior.

Fix plan:

1. Add direct budget intent handling before event qualification:
   - Budget-sensitive birthday
   - Price objection
   - Discount/coupon/promo/offers
   - “too expensive”
2. Use safe deterministic wording when exact price/discount is unavailable:
   - Acknowledge budget concern.
   - Explain that final amount depends on date, location, group size, and package.
   - Offer a lower-friction path: escape-room only vs package.
3. If using `knowledge/faq.txt` discount values, mark them as approved business facts first. If not approved, do not quote numbers.
4. Do not ask for name/phone before answering the budget question.

Validation scenarios:

- “I want a birthday, but budget is tight.”
- “Do you have discounts?”
- “That sounds expensive.”
- “Any student offer?”

Expected style:

“Totally fair to watch the budget. The simplest path is escape-room only; the fuller birthday path adds food or activity support. I don’t want to guess the final amount, but I can help narrow the location, date, and group size first.”

## Implementation Priorities

### P0: Direct-Answer Guard

Files/functions:

- `src/services/question_classifier.py::QuestionClassifier.classify`
- `src/agents/inbound_agent.py::_fallback_response`
- `src/agents/inbound_agent.py::_get_faq_or_knowledge_answer`
- `src/agents/inbound_agent.py::_answer_faq`
- `src/orchestration/conversation_manager.py::determine_routing`

Add deterministic direct-answer handling for:

- Confusion / escape-room education
- Frustration repair
- Budget/discount/price objection
- Horror/thrill preference
- Slot comparison
- Location recommendation

This is the highest impact because it prevents qualification from interrupting clear customer questions.

### P1: Recommendation Engine Expansion

Files/functions:

- `src/services/recommendation_engine.py::RecommendationEngine.recommend`
- `src/services/recommendation_engine.py::RecommendationEngine.available_options`
- new helper if needed: `RecommendationEngine.compare_options`

Add inventory-safe recommendation behavior for:

- Horror/scary/thrill
- Intermediate/not-too-easy
- Room comparison
- Location-aware recommendation
- Large group-safe alternatives

### P1: Knowledge Retrieval Safety and Specificity

Files/functions:

- `src/knowledge/demo_knowledge.py::get_demo_answer`
- `knowledge/faq.txt`
- `src/agents/inbound_agent.py::_get_faq_or_knowledge_answer`

Changes:

- Comparison queries must not return room descriptions.
- Location recommendation queries must not return only a branch list.
- Discount/price answers must only quote approved facts.
- Escape-room education must cover more natural variants.

### P2: Deterministic Response Quality Composer

Files/functions:

- `src/agents/inbound_agent.py::_recommendation_response`
- `src/agents/inbound_agent.py::_guided_response`
- `src/agents/booking_agent.py::_append_booking_resume`
- `src/services/conversation_intelligence.py::ConversationIntelligenceLayer`

Add reusable deterministic style helpers:

- Answer first.
- One question at a time.
- No name/phone before help.
- Resume booking after FAQ/interruption.
- Keep responses under voice-friendly length.

This is not an OpenAI prompt-composer. It is deterministic response shaping.

## Conversation Intelligence Layer Usage

The conversation intelligence layer should support production behavior, not only post-call reporting.

Recommended additions:

1. Track `last_direct_question_answered`.
2. Track `repair_needed` for phrases like “not what I asked.”
3. Track `ignored_preference_risk` when the user states horror/thrill/budget/location preference and the agent asks an unrelated qualification question.
4. Expose lightweight flags back to `InboundAgent`:
   - `needs_repair_response`
   - `needs_direct_answer`
   - `preference_to_reflect`

These flags should produce deterministic recovery responses in the current backend.

## Non-Goals

- Do not assume prompt rewriting will fix these failures.
- Do not modify provider booking semantics for conversation-quality fixes.
- Do not invent prices, discounts, capacities, availability, or unsupported “best” claims.
- Do not weaken booking confirmation safeguards.
